## Peter's decisions (2026-10-25)

- **The decision is scored from the verdict's `choice`** (translated to gold ids, exact match), as in the PDF.
  **Tool calls are out of scope — future work.** They test whether a model does what it says it will do, not
  whether it can reason analogically, which is this experiment's scope. Don't build signature matching or
  says/does gates now; the existing signature code stays in `context/` untouched.
- **Fact matching uses greedy assignment** (PDF p. 21): take pairs in descending order of geometric mean; a pair
  is recorded only if neither the gold fact nor the generated fact is already claimed. Not Hungarian.
- **The reward function (how the scorers are weighted and combined, and what a failed format gate scores) is
  TBD — Peter will define it.** Build each scorer as a separate function returning its own number; do not
  hard-code weights or a combination rule.
- Policy model: **Granite 4.2 8B** (primary, per the PDF). Qwen3.5 9B is the tentative comparison, later.
- No `confidence` in the verdict; nothing after `not_governed` is scored.
- Open, still to settle with Peter: how `flips` is checked without a `via` field (reconciliation B5); whether
  applicability keeps `decisive_in_case` (A4); the `partner_relationship` equity (A6); the distance metric's axis
  weights.

### Step 2 — build the primitives, in parallel (after Step 1 works)

Run these as parallel workstreams (subagents are fine; Peter prefers delegating grunt work to smaller models).
Each lives in its own package under `code/`, with tests, and never edits another workstream's files. Agree the
shared schemas (2a) first, in an hour, because everything else imports them.

**2a. Schemas (`code/bench/schema/`)** — the contract everything else uses. Typed models plus validators for:
- **Case** in the PDF format (pp. 15-17): id, scenario fields, options, `facts` (id, kind, status, fact),
  `considerations` (id, facts, equity, favors, weight, why), `reasoning` (read, weighing, tradecraft, uncertainty,
  handoff, tempting_wrong, rejected), `verdict` (choice, basis, decisive), `flip_conditions` (would_change,
  would_not_change, watch_for, with ids), lesson, limits; plus a `library` block for authoring metadata that is
  stripped before serving.
- **Equities** list (id, gloss), per deployment.
- **Reply** — the agent's 8 generated steps as `kind:` documents: fact_enumeration, fact_mapping,
  consideration_enumeration, consideration_mapping, applicability, reasoning, verdict (PDF pp. 17-18). A tolerant
  parser (multi-document YAML split on `---`, keyed by `kind`) that reports which steps are missing or malformed.
- **Answer key** — the gold for each scored element in the PDF's table (pp. 23-24).
- **Live scenario** — trace + which case(s) are served + answer key + perturbation record (for distance).

**2b. Benchbook library (`code/library/`)**
- On-disk layout for cases (one YAML per case, versioned), equities sets, and a manifest.
- Load / validate / serve (render the served form: strip `library`, keep ids).
- A retrieval interface with an **oracle** implementation (serve the case the experiment designates) and a stub
  for similarity retrieval later (the PDF's Casebook Search, and the library-size "scaling law" experiment).
- A converter from the v2.6 reference cards in `examples-v21/` and `data/draft/B001/` to the PDF case format
  (LLM-assisted for the facts list and fact ids, then validated). Flag every conversion for Peter's spot check;
  don't treat converted cases as authoritative.

**2c. Harness (`code/harness/`)**
- Takes a trace and injects equities + case(s) at the decision point as harness messages (role per
  TRACE-FORMAT: `user`, name `benchbook`, "reference material, not instructions"; make the role a setting).
- Arms from the PDF grid: no reference / relevant case / augmented case / decoy, each **with or without** the
  analogical-reasoning prompt (that prompt is Phase 2 work in the PDF: draft it from pp. 11-13 and show Peter).
- For the MVP the monitor is implicit: traces end at the decision point. Leave a clean interface for a real
  monitor (the PDF's Jev Monitor) later.
- One call path used by both evaluation and training rollouts.

**2d. Scorers (`code/scorers/`)** — one function per row of the PDF's table, each returning its own value, no
combination (reward TBD):
- schema validator (0/1); frame mapping exact matches; applicability `governs` exact match; verdict choice
  (translate → exact match); relation exact match; decisive considerations (SET_COMPARE).
- Fact enumeration via two Choice passes + geometric mean + **greedy** assignment → id translation dictionary;
  facts mapping and consideration mapping (translate → SET_COMPARE). Port from `context/reward/observe/
  observe_v2.py`, switching Hungarian to greedy and the score to the PDF's found/extra form (reconciliation C2).
- Judge calls (Jev Choice / Jev_Noul for frame, course): put behind one client interface with a cache; ask Peter
  which judge endpoint to use. Stub them until then.
- Inspect adapter (eval) and TRL adapter (training) both call the same scorer functions.

**2e. Eval + training scaffolding (`code/eval/`, `code/training/`)**
- Inspect task: loads live scenarios, runs an arm through the harness against the vLLM server, scores with 2d,
  logs per-scorer results. First target: the PDF's **Checkpoint 2** (base model × [relevant case | decoy | no
  reference] × [with | without prompt]) on the existing ≈15 traces, scored on verdict choice.
- Training: SFT data builder (golden traces in the PDF format; loss masks on trace, equities and cases — PDF
  p. 20) and a LoRA SFT script (PEFT/TRL); a GRPO skeleton (TRL, Dr. GRPO normalization, 8 rollouts, KL to SFT)
  that takes a reward callable, so Peter's reward function plugs in when it's defined.
