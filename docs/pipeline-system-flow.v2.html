Benchbook Data Pipeline

Every step from raw sources to SFT, RLVR and eval records: which model runs it, exactly what goes into its context, what comes out, and where each piece of the gold comes from. Drafted for Peter to check. Source of truth: context/DATA-PIPELINE-DESIGN-v2.md and BUILD-BRIEF-2f-2026-10-25.md in the repo.

Notation

RRaw corpus: immutable source documents, addressed by span ids.
E · E_dEquity registry (shared ids + glosses); E_d is one deployment's injected subset (~10–20).
DDeployment profile: role, tools, standing orders, delegations, people.
X = (F, Q, A)A scenario. F facts · Q question frame (question, decider, agent role, options) · A answer.
A = (K, W, V, Φ)K considerations (fact → equity → favors → weight → why) · W reasoning prose · V verdict · Φ flip conditions.
C · TRoles: a scenario served as a case (card) or rendered as a trace. Any scenario can be either.
τ · σ · αThe rendered trace; its span map (where each fact landed, how); the allowed list (true details not in F_T).
GGold for a pair: F_T, Q_T, M^F, K_T, M^K, applicability, relation, via, V_T.
YA reply in the PDF step format (the SFT target, and what the policy writes at runtime).

The gold (G) is assembled by code from what extract, perturb and pair already recorded. No model writes any part of the RLVR answer key. A model writes only the SFT text, and that text is kept only when its structure matches G.

At data-generation time nothing ever extracts facts from a trace. F_T is known before the trace is rendered. Only the policy, and the SFT writer standing in for it, reads the trace.

Equities: the variable to isolate

Equities enter in three places: extract (K is written in E's vocabulary), the independent solve, and the harness prompt (E_d is injected with the case). Because the harness injects them together, "case helps" and "equities help" are confounded. The PDF's question of whether the harness alone is enough is answered by the base-model rows, before any training, only if equities and the case vary independently.
